Companion · cross-node trust & the data backbone

Autonoetic — Federation & Data Model

Three structural pictures the other maps don't reach: how independent gateways decide to trust each other across the wire, how the single database that records everything is actually wired together, and when a promotion gate is allowed to trust its own prior verdict.

Fourth companion to the governance, technical, and runtime-dynamics maps. §A is the one dimension none of them touch — trust between nodes. §B is the schema behind all the audit and activation the others describe. §C is trust across time: reusing a verdict for bytes that provably did not change.

§ A — Topology

Federation — trust across nodes (OFP)

Two gateways cooperate over the OpenFang Protocol only if each can verify the other runs compatible law — the constitution-digest handshake — never because they know each other's internals or reputation. Membership in the federation is operating under verifiable shared law.

The handshake — verified on both sides
Initiator
Receiver
1Sends Handshake: node_id, fresh nonce, auth_hmac = HMAC(secret, nonce+node_id), constitution_digest, ConstitutionProfile, advertised extensions.

P-10.9 — when are two constitutions "compatible"?
Exact

Digests match

The peer's constitution_digest equals the local one — byte-identical law.

KnownCompatible

On the allowlist

Exact, or the peer digest is in the configured known_compatible_digests set.

Superset

Peer ⊇ local

Every local rule/right enforcement entry appears in the peer's ConstitutionProfile with an identical citation. The peer may add clauses; it may not drop or diverge on any local one.

Missing peer digest is rejected unless allow_missing_peer_digest is set. The check runs in evaluate_constitution_compatibility on both the receiver (handshake) and the initiator (ack). This is where "trust is structural, not personal" is mechanically true: acceptance is a function of law-compatibility and a shared secret — nothing about identity or track record.

The wire & what's actually built

The protocol

autonoetic-ofp is a wire crate only — JSON over TCP, 4-byte length prefix, PROTOCOL_VERSION 1, wire-compatible with OpenFang. A WireMessage carries {id, signature?, seq_num?, kind}. The negotiated msg_hmac extension adds a per-message HMAC signature + monotonic seq_num (integrity + replay protection).

Request: Handshake · AgentMessage · ChainAttestation · Ping · Discover · Capsule*
Response: HandshakeAck · AgentResponse · Pong · Error · Capsule* Notify: AgentSpawned · AgentTerminated · ShuttingDown

Shipped vs. deferred

shipped — the HMAC handshake, extension negotiation (msg_hmac, resilience), per-message signing, digest+profile exchange with all three compatibility modes, Ed25519 chain attestations, and AgentMessage forwarding (P-10.6) with Ping/Pong.

deferred — Discover, the Capsule* transfer family, and all notifications return 501 Not Implemented inbound; HandshakeAck.agents is a hardcoded empty TODO. Cross-node capsule emigration is defined at the wire level but not server-wired; cross-node promotion is not an OFP feature at all.

Four things called "federation" — keep them apart

OFP node federation (§ A, this sheet) is cross-machine TCP between gateways. It is not federation_escalate — a local in-process tool that escalates promotion verdicts to the operator — not the promotion jury (auditor + evaluators) that gates a revision — and not federation carry-forward (§ C), which reuses a prior jury verdict across a rebuild and never touches the wire at all. Same word, four architecturally distinct mechanisms.

§ C — Verdict Reuse

Carry-forward — when a gate need not look twice

A jury verdict is recorded against the whole-artifact digest, so any rebuild voids all three verdicts — even a one-line SKILL.md prose fix that leaves code and contract byte-identical. One real promotion re-ran a 42-test unit_test_runner and an auditor LLM review three times over, neither of which reviewed anything that had changed. Carry-forward narrows the binding from this gate reviewed the whole artifact to this gate reviewed a specific subset of it — where the subset is fixed and gateway-owned, never agent-named.

Three digests, not one — each gate carries only if what it read is unchanged
digestcoversgates that read it
code_digestevery file classified code: script_entry, sources, tests, dependency manifests, and runtime.lock's dependency/artifact/layer set — deps change what the tests can importunit_test_runner · auditor · sealed_evaluator · static_evaluator
contract_digestcanonical JSON of the semantic frontmatter fields — what the gates verify against — normalized from either accepted SKILL shapeall four
prose_digesteverything else: the SKILL.md prose body, names and descriptions, README, examples, commentsstatic_evaluator only
classification

Gateway-owned, never agent-supplied

Which bucket a file or field lands in is mechanical. A frontmatter field in neither the contract table nor the known-prose list defaults to prose and is logged, so an unclassified field is visible during rollout rather than silently downgrading a gate. If the agent could name its own classification, it could rename code as prose and carry a verdict over a rewrite.

the asymmetry

The planner reasons; the gateway verifies

The planner proposes a carry by naming the prior artifact; the gateway accepts only on a content-addressed digest match against its own recomputation, and rejects anything below the configured floor. The planner never reads the strictness value — it simply receives rejections. Proposing is cheap and unprivileged; accepting is neither.

audit

A carried verdict can never pass as fresh

Each role verdict reports its input_coverage and either fresh: true or carried_from with the prior ref, role, timestamp and justification. The approvals surface marks it ↻ carried; a federation.carry_forward causal event is emitted per accepted carry; carry_forward_lineage makes the chain walkable back to its root.

The strictness dial — an operator floor, defaulting to today's behaviour
levelcarries when…never carries when…
off defaultnever — every rebuild re-runs every gatealways
conservativea code-reviewing gate's code_digest and contract_digest are both byte-identical — i.e. only prose movedcode or contract changed at all

static_evaluator never carries

It reads all three digests, so its verdict is reusable only when nothing changed — which means no rebuild happened. Carry-forward therefore only ever helps the three code-reviewing gates. That is correct rather than unfortunate: static_evaluator is the manifest gate, and the manifest is exactly what a prose-only rebuild touches.

Off by default, and fail-closed when on

An upgrade changes no behaviour until an operator opts in per environment. Every failure mode — a missing digest, an unresolvable prior ref, a recorded digest that doesn't match the recomputation — refuses the carry and re-runs the gate. A row lands in carry_forward_lineage only after verification accepted, so rejected claims leave no trace suggesting they were honoured. The floor is a ceiling on permissiveness, not a mandate: the planner may always be more conservative than it allows.

§ B — Entity-Relationship

The gateway database

One SQLite file (gateway.db, schema v80) holds all transactional state — some seventy tables. Most relationships are logical joins on shared columns, not declared foreign keys. Four spine columns carry the whole model. A newer egress label plane (v73–v79, data-envelopes track) threads an egress_label_json through the durable stores and keys taint by session; v80 adds carry-forward lineage (§ C).

The clusters below map the load-bearing tables — the ones with independent identity and cross-cluster relationships. They are not the complete list: pure child/index tables, per-feature state tables, and search mirrors are omitted deliberately. migrate.rs is the authority on the full set.

The spine — four columns thread every cluster
root_session_id

The workflow/run root. Bridges to workflow_id via workflow_index; keys reports, bindings, grants, escalations.

workflow_id

The workflow. Keys task runs, events, approvals, interactions, emergency stops.

session_id

A single agent session. Keys causal events, traces, bindings, transcripts.

event_id

The universal correlation key. PK of causal_events; join column of execution_traces and hook_deliveries.

The core relational spine

Read it as two stories. Activation (blue): a session binds to a pinned revision — workflow_index → session_agent_bindings → agent_aliases → agent_revisions — where the alias is the single source of truth for "active" and revisions are immutable and self-referential (base_revision_id). Audit (teal): execution_traces and hook_deliveries join causal_events by event_id — the correlation key everything reconstructs from.

Carry-forward

carry_forward_lineage PK artifact_id · role→ source_artifact_id/_ref; strictness, source_code_digest, source_contract_digest (v80)
One row per (artifact, carried gate role), written only after verify_carry_claim accepted — so rejected claims never appear. Answers "who did you carry from", and walks back to the root of the lineage.

Two properties worth noting across the model. Several tables are append-only or insert-only — causal_events, security_findings — matching the immutability guarantees on the technical map. And the pure child/index tables (memory_tags, the *_fts search mirrors, short_id_index, task_claims) have no independent identity — they exist only to serve their parent, which is why they carry no spine column of their own.
